## สิ่งที่เรียนรู้ที่ใช้กับปัญหาเรา (เรียงตามความคุ้ม)

1. **ภาพ render ต้องกรอง "background รั่ว" ก่อนจับคู่ (CRISTAL)** วิธีของเขา: z-buffer เอาความลึกต่ำสุดต่อพิกเซล, เฉลี่ยสีเฉพาะจุดในช่วงความลึกใกล้, กรองความลึกแบบลำดับชั้นเพื่อตัดจุดไกลที่ลอดช่องว่าง แล้วเติมรูด้วย U-Net (ได้ผลมากกับ point cloud เบาบาง) renderer ของเรามี z-buffer + เติมรูด้วย distance transform แต่ **ไม่มีตัวกรองจุดรั่ว** ซึ่งตรงกับภาพ render ที่เห็น (จุดพื้น/ผนังไกลทะลุเป็นหย่อม) ใส่ตัวกรองแล้ว (`M1_LEAK`, `vps/m1lf.py`) กำลังทดสอบบน oldtown12 และ grid11
2. **จัดแนวด้วยเรขาคณิตล้วน แทนการจับคู่สี (SemCityLoc)** ค้นหาโพสในลูกบาศก์ 4 มิติ (x, y, z, yaw; roll/pitch คงที่จาก gravity) รอบ prior ด้วยต้นทุน IoU ของ semantic mask แล้วขัดละเอียดด้วย particle filter โดยจัดแนวความลึกที่ทำนายจากภาพ (MoGe-2) กับความลึกที่ render จากโมเดล (หา scale/shift ด้วยกำลังสองน้อยสุดต่อโพส, ถ่วงน้ำหนักด้วย 1/ความลึก) ผล: recall ที่ (2 ม., 2°) 35% → 69%, error เฉลี่ย 9.89 → 2.62 ม. บนฉากตึกชิด (UAV ที่ 75 ม., ภาพจริง) **ความหมายกับเรา:** แผนที่ LiDAR ของเรามีเรขาคณิตที่แม่นอยู่แล้ว ปัญหาคือสี/texture ดังนั้นเปรียบเทียบ "ความลึกที่ทำนายจากภาพหุ่น" กับ "ความลึกที่ render จากแผนที่" ได้โดยไม่ต้องใช้สี และไม่ไวต่อมุม calibration ของการลงสี ข้อควรระวัง: ถนนยาวตรงมี ambiguity ตามแนวถนน (ต้องใช้ prior/odometry), ความลึกเดี่ยวจากกล้องเดียวคลาดเคลื่อน, และ semantic head ต้องฝึกกับโดเมน (zero-shot ได้แย่กว่ามาก: recall 16% เทียบ 69%) ต้องดาวน์โหลด MoGe-2 (อนุญาตแล้ว แจ้งขนาดก่อน)
3. **MINIMA: จับคู่ RGB กับภาพ "ความลึก" โดยตรง** ได้รับการฝึกให้ทำ RGB↔Depth (depth จาก DepthAnything V2) และทดสอบกับชุดจริง DIODE: ทางลัดของข้อ 2 คือ render *depth* จากแผนที่ LiDAR ไม่ใช่สี แล้วใช้ MINIMA (sparse แบบ LightGlue หรือ dense แบบ RoMa) จับคู่กับภาพหุ่น ใช้ pipeline PnP เดิมได้ทั้งหมด
4. **calibration แบบไม่ใช้เป้ายังไม่แม่นพอสำหรับข้อกำหนดของเรา:** วิธี 2DGS ที่ดีที่สุดได้ rotation error 0.36–0.43° (translation ~9 ซม.) บนชุดของเขา ขณะที่ในการทดลองของเรา 0.5° ทำให้ความแม่นละเอียดลด 41% → 10% และข้อกำหนดที่ผมประมาณคือ ≤0.1–0.2° ดังนั้น (ก) ต้อง calibrate แบบมีเป้าและตรวจละเอียด หรือ (ข) ใช้ข้อ 2–3 ที่ไม่ผูกกับสีเลย
5. **FAST-LIVO2 ยืนยันว่ากล้องช่วย LiDAR เสื่อมได้จริง** แต่ผลของเขาใช้ฉากมี texture ซิมของเรา (พื้นเทาเรียบ) อาจไม่ได้ประโยชน์ และเป็นระบบ ROS 1 ต้องพอร์ต ใช้เป็นทางเลือกระดับระบบสำหรับกรณี suburb13 ไม่ใช่งานเร่งด่วน
6. **XFeat ทนโมดัลลิตี้ต่างไม่ดี (XFeat Revisited)** สอดคล้องกับที่ DISK+LightGlue ชนะ XFeat ในความแม่นละเอียดของเรา
7. **DiskChunGS** แบ่ง scene เป็น chunk เก็บบนดิสก์ โหลดเฉพาะที่เห็นอยู่เข้า GPU: เป็นแบบอย่างของแผน tile/LOD (C-sync) ถ้าจะใช้ 3DGS เป็นแผนที่
8. **RoMa v2** แม่นกว่าแต่หนักกว่า (1.7× เร็วกว่า RoMa เดิมบน H200; ยังไม่ทราบตัวเลขบน 8 GB) ใช้ได้ในขั้น refine ที่ตำแหน่งเดียว ไม่ใช่ทุก view
9. **CLIDD** อ้าง descriptor เล็ก 99.7% และเร็ว >200 FPS บนอุปกรณ์ edge (ยังไม่ทดสอบ; น่าสนใจถ้าต้องรันบนบอร์ดเล็ก)

## ผลจากการอ่านฉบับเต็มรอบที่สอง (ตัวเลขจากตาราง/ข้อความในไฟล์)

**CRISTAL (2511.16349), อ่านครบ 9 หน้าเนื้อหา**
- เขาจับคู่ภาพจริงกับภาพ render ของ LiDAR สี ด้วย XFeat (ไม่ใช่ LoFTR/DISK) + PnP; โหมด "tracking" = render ที่ pose ก่อนหน้าแล้วจับคู่กับเฟรมใหม่ (คล้ายโหมด prior ของเรา); relocalization = cubemap ที่สุ่มทั่วแผนที่ + PnP + **refine ด้วยการ render ซ้ำที่ pose ที่ประมาณได้**
- **ตาราง 3 (สำคัญ):** ที่ความหนาแน่นเต็ม (71 ล้านจุดในห้อง 6×6 ม.) render แบบจุดธรรมดาใช้ได้ (error 0.021 ม., 1.03°) แต่เมื่อลดจุดเหลือ 33% มุมคลาด 7.7° (neural: 0.65°) และเหลือ 10% หา pose ได้เพียง 210 จาก 4305 เฟรม (neural: 4305 ทั้งหมด, 0.65°) **neural renderer (กรองจุดรั่วตามความลึก + เติมรูด้วย U-Net) จึงจำเป็นเมื่อจุดเบาบาง**
- **เทียบกับเรา:** แผนที่เรามีราว 2.5 ล้านจุดต่อ 200×200 ม. (ห้องของเขา ~71 ล้านจุดใน 36 ตร.ม. หนาแน่นกว่าต่อพื้นที่หลายหมื่นเท่า และแม้ลดเหลือ 10% ก็ยังหนาแน่นกว่าของเรามาก) ภาพ render ของเราจึงเบาบางกว่าสิ่งที่เขาทดสอบ การพึ่ง point-based render ธรรมดาในโลกใหม่ (ตรอกแคบ ผนังใกล้) น่าจะเป็นสาเหตุสำคัญที่ matching ตาย (match เฉลี่ย 7–11)
- ข้อจำกัดของเขา: ฉากภายใน/สังเคราะห์ที่ถ่ายด้วยสแกนเนอร์ตั้งพื้น ไม่ใช่แผนที่ทางอากาศเบาบาง; ไม่มีการทดสอบผนังไกลมากๆ

**MegaLoc (2502.17237), อ่านครบ**
- ฝึกด้วยภาพถ่ายจริงห้าชุด (GSV-Cities, MSLS, MegaScenes, ScanNet, SF-XL); DINOv2-B + SALAD (8448 มิติ) ไม่เคยเห็นภาพ render
- **จุดอ่อนที่เขาระบุเอง:** ฐานข้อมูลที่ไม่ครอบคลุมทิศ (กรณี MSLS), สภาพธรรมชาติแปลกๆ (ป่า ถ้ำ) และ **ไม่แนะนำให้ใช้บนอุปกรณ์ฝังตัว** สอดคล้องกับ retrieval ที่ติด top-50 แค่ 10–45% ในโลกใหม่ของเรา

**MINIMA (2412.19412), อ่านตารางหลักครบ**
- ตารางสังเคราะห์ RGB↔Depth (AUC@10° ของ pose): LightGlue เดิม 2.87, LoFTR 0.44, RoMa 22.75; **MINIMA-LG 32.5, MINIMA-LoFTR 28.8, MINIMA-RoMa 48.6** (ชุด MegaDepth มุมกล้องต่างกันมาก)
- ชุดจริง RGB-Depth (DIODE, ความผิดของ homography AUC@5px): LG 3.3, LoFTR 4.2, RoMa 24.6; MINIMA-LG 26.8, MINIMA-RoMa 50.9
- **ความหมาย:** matcher ปกติ (รวม LightGlue ที่เราใช้) **แทบจับคู่ RGB กับภาพความลึกไม่ได้เลย**; MINIMA ช่วยได้มากแต่ค่าสัมบูรณ์ยังปานกลาง และ MINIMA-RoMa ใช้เวลา ~633 มิลลิวินาทีต่อคู่ (RTX 3090) จึงใช้เป็นขั้น refine ที่ pose เดียวได้ ไม่ใช่ค้นทุก view

**SemCityLoc (2606.27444), อ่านครบ**
- เวลา 0.878 วินาทีต่อภาพ (โมเดล 0.116 + ค้นหยาบ 0.409 + particle filter 0.353; nvdiffrast); prior เพี้ยนได้ถึง ±50 ม./แกนโดย recall ลดน้อย (2 ม./2°: 62.8%) แต่เกิน 100 ม. ตกหนัก
- **โมเดล LoD1 (กล่องตึกเรียบง่าย) ก็ให้ 48.9% ที่ (2 ม.,2°)** และ LoD2 69.1% แสดงว่าเรขาคณิตระดับอาคารแบบหยาบ + ความหมายพอสำหรับจัดแนวได้ ผลที่ดีไม่ได้มาจากความหนาแน่นของเรขาคณิตเพียงอย่างเดียว
- ข้อจำกัดที่เขาระบุ: ฉากที่เห็นอาคารเดียว/ผนังเดียวจะกำกวม; ต้องฝึก segmentation กับโดเมน (zero-shot CLIP+SAM ได้ mIoU 32% และ recall ตก)
- เป็นงานโดรนอากาศ (UAV 75 ม.) ไม่ใช่กล้องระดับพื้น

**DiskChunGS (2511.23030)**: 3DGS SLAM จากกล้องล้วน (ORB-SLAM3 + depth-anything) แบ่ง chunk เก็บบนดิสก์ ผ่าน KITTI ทั้ง 11 sequence และรันบน Jetson Orin ไม่ใช่ LiDAR; เป็นแบบอย่างของการจัดการหน่วยความจำแบบ tile ไม่ใช่วิธีหาตำแหน่ง
**CLIDD (2601.09230)**: descriptor distill จาก ALIKED-N32, เร็ว (>200 FPS บน edge) ลดขนาด 99.7% เหมาะกับบอร์ดเล็ก ไม่ได้แก้ปัญหา "ช่องว่างโดเมน" ที่เราติด

**3DGS-ReLoc (2403.11367), อ่านครบ**
- ข้อมูลจริง KITTI-360, แผนที่ = 3D Gaussian Splatting ที่เริ่มจาก LiDAR สีแล้วฝึกด้วยภาพ (จากการขับรอบแรกของถนนเดียวกัน), query = การขับรอบสอง (revisit) ไม่ใช่โดรน
- ค้นเริ่มต้นแบบ brute-force: render ภาพจาก submap รอบตำแหน่งหยาบ (±10 ม. ทั้ง x,y และ ±90° yaw) เทียบ NCC กับภาพจริง (กริด 2 ม./10°, ค้น ±15 ม. และ yaw ทั้งวง) สำเร็จ 98.2% และ 98.7%; จากนั้น refine ด้วย SuperPoint+LightGlue และ render ซ้ำที่ pose ที่ประมาณ → error 0.10–0.19 ม., 0.25–0.54°; โหมดสดด้วย constant-velocity: APE RMSE ~0.10 ม.
- **ข้อควรระวังเมื่อเทียบกับเรา:** แผนที่ถูกฝึกด้วย **ภาพระดับถนน** จากยานพาหนะที่ขับผ่านถนนเดียวกัน จึงมีสีของผนังระดับถนนครบและเป็นภาพ "ที่ฝึกให้เหมือนจริง" ส่วนแผนที่ของเราสร้างจากโดรนที่ไม่เคยเห็นผนังระดับถนน (ช่องว่างข้ามมุมมอง) งานนี้จึงไม่ได้พิสูจน์กรณี aerial→ground แต่ยืนยันว่า (ก) render+จับคู่ได้ดีเมื่อแผนที่มีข้อมูลระดับถนน (ข) การค้น NCC+refine ใช้ได้กับ prior หยาบ ±10 ม.
- KITTI-360 ใช้เช็ค "ช่องว่าง render↔ภาพจริง" ของ renderer เราได้บางส่วน (แผนที่จากรถ ไม่ใช่โดรน) ต้องลงทะเบียนเพื่อดาวน์โหลด (ผมทำแทนไม่ได้) และใบอนุญาตเป็นแบบไม่ใช้เชิงพาณิชย์ (ต้องตรวจเงื่อนไขก่อนใช้)

## ที่ยังไม่ได้อ่านลึก / ไม่ควรอ้างเกินจริง
- ตัวเลขของแต่ละงานเป็นชุดข้อมูลของเขา (UAV จริง, ขับรถ, ในอาคาร) ไม่ใช่ของเรา; ไม่ได้ทำซ้ำผลของใคร
- MegaLoc อ่านเฉพาะหัวข้อ failure cases; RoMa v2/MINIMA ไม่ได้อ่านการทดลองทั้งหมด
